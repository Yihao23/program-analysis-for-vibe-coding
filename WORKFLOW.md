# Workflow: let an AI agent write the code, keep it under control with a gate

Companion documents: `CONCEPT-MAP.md` (concept ↔ code) · `README.md` (running the demo)

This document answers one question only: **when the code is generated by an agent, what do the human, the agent and the gate each do, in what order, and which lecture concept sits behind each step.**

---

## 0. Three roles

```
   human     chooses the abstract domain (decides what to look at) · writes specs (decides what is wanted) · reviews changes in the trusted zone
   agent     generates code under the specs and constraints · fixes using the gate's counterexamples · never touches the abstract domain
   gate      answers Next(I) ⊆ I ? for every change · every ✗ must carry a counterexample · never judges "correct or not" on the human's behalf
```

---

## 1. Starting a project: build the gate before the first line of business code

```
① CLAUDE.md          write down the protocol and the intended trust zones. No code yet, only intent
② declaration area   the five constants at the top of the gate: TRUSTED / CONTRACTS / K / ESCAPE_HATCHES / TIDY_ARGS
                     the check functions may still be empty — first fix "what to look at"
③ specs/ skeleton    framework + at least one lower and one upper; add a hyper observer if there is cross-module behaviour
④ gate check all ✓   make it pass on the empty project
⑤ only then app/
```

The order cannot be reversed: I must exist before `Next(I) ⊆ I` means anything. Write code first and add the gate later, and the first check is a pile of ✗ — you will be forced to loosen I to accommodate the code. The abstract domain ends up defined by the code instead of the other way round.

---

## 2. The loop for each feature

```
   human   writes the spec: SPEC(lower, …) says "must be able to", SPEC(upper, …) says "must never"
            │        cross-module relations go into the INVARIANT block at the module entry + one cross-file spec
            ▼
   agent   reads CLAUDE.md, the declaration area, the relevant INVARIANT blocks → implements
            │
            ▼
   gate    gate check <changed files>
            │
            ├─ upper ✓ lower ✓   → untrusted zone: merge. trusted zone: wait for review
            ├─ upper ✗           → counterexample back to the agent. No human needed
            └─ upper ✓ lower ✗   → the agent did not do what was asked: change the prompt or refine the spec, back to the human
```

### What the report looks like

The output of `gate check` is "the report". Baseline (all ✓):

```
GATE REPORT     Next(I) ⊆ I ?
UPPER  constraints — must never
  ✓ build
  ✓ arch
  ✓ escape
  ✓ K
  ✓ reduce
  ✓ clang-tidy
  ✓ upper        1 passed, 0 failed
LOWER  examples — must be able to
  ✓ lower        2 passed, 0 failed
HYPER  hyperproperties
  ✓ noninterf    both worlds agree on the ledger: 10.00 2.68 0.12 100.00
VERDICT  upper ✓ lower ✓ → mergeable
```

Same gate, different code (scenario 4: features change global rounding via a forward declaration):

```
GATE REPORT     Next(I) ⊆ I ?
  changed: app/features/promo.cpp   [untrusted]
UPPER  constraints — must never
  ✓ build
  ✓ arch                                   ← the #include check cannot see a forward declaration
  ✓ escape
  ✓ K
  ✓ reduce
  ✓ clang-tidy
  ✓ upper        1 passed, 0 failed
LOWER  examples — must be able to
  ✓ lower        2 passed, 0 failed
HYPER  hyperproperties
  ✗ noninterf    features/ changed billing's behaviour (implicit flow):
                   without features: 10.00 2.68 0.12 100.00
                   with features:    10.00 2.67 0.12 99.99
VERDICT  upper ✗ lower ✓ → did what was asked, but crossed a line (reject, no human needed)
```

How to read it:

```
report              = everything the gate knows about the code = α(code) = one point in the abstract domain
each line           = one axis of the abstract domain; its value is ✓ or ✗ + detail
detail after a ✗    = the counterexample — the agent takes it and fixes, no human translation needed
VERDICT             = the combination of whether the upper side (UPPER + HYPER) and the lower side (LOWER) contain a ✗
```

Everything outside these eleven lines (variable names, which algorithm, whether there is a function nobody calls) is not in the report — that is the part the gate cannot distinguish, i.e. γ.

---

## 3. What to do with each of the four VERDICTs

```
upper ✓ lower ✓    untrusted zone: merge          trusted zone: merge after human review
upper ✓ lower ✗    the agent did not do what was asked. First check whether the spec is clear, then decide: new prompt or better spec
upper ✗ lower ✓    did it but crossed a line. Counterexample back to the agent, no human — this cell is what takes the human out of the bottleneck
upper ✗ lower ✗    reject. Usually the agent misunderstood the task; rewrite the prompt
```

## 4. The concept behind each step (plain words)

Each row: **a step in the workflow → the lecture concept → one plain sentence on why it is there**.

### Starting a project

| Step | Concept | Plain words |
|---|---|---|
| ① write CLAUDE.md first | 01 Rice's theorem | There is no such thing as "check whether the code is correct"; you can only check specific things one at a time. So decide first what to check |
| ② the five constants in the declaration area | 02/05 abstract domain | You decide which dimensions to look at, and those are the only dimensions you can see. This is a trade-off the human makes for the project; the agent must not |
| ② CONTRACTS | 02/03 an invariant must be expressible in the domain | A rule that is not written down does not exist for an agent. Write it in machine-readable form and it exists |
| ② TRUSTED / UNTRUSTED | 09 integrity lattice | Code someone has vouched for and code nobody has looked at are two levels; the latter must not influence the former |
| ② K | 03b threshold set | Constraints for the agent are hard numbers like "no more than 40 lines", not "depends". Hard numbers converge fast |
| ② ESCAPE_HATCHES | 07 the generator optimises against the check | The agent's goal is a green gate. NOLINT is the shortest path, so it has to be blocked |
| ③ specs before app | 04 α vs spec | Code can only tell you what it does, never whether that is what you wanted. "What is wanted" has to be written separately |
| ③ one lower + one upper | 07 Bilateral | Examples say "must at least do this"; properties say "must never exceed this". With only one side the agent finds a loophole |
| ③ hyper observer | 09 hyperproperties | Some things cannot be seen in one run ("did A secretly influence B"); you need two runs to compare |
| ④ empty project passes with all ✓ | 02 Init ⊆ I | The starting point must be inside the rules; only then can every later step ask "still inside?" |

### What each symbol in the formulas stands for

The formulas that appear above, symbol by symbol, mapped onto the workflow.

**`Next(I) ⊆ I`** (gate check)

```
I         all the gate's conditions taken together — the "healthy state"
Next      one change by the agent
Next(I)   what the healthy state becomes after this change
⊆ I       still healthy
```

**`l ⊑ γ(α(l))`** (the agent reads the declaration area first)

```
l         the real code
α         the gate: computes a report from the code
α(l)      the report
γ         the other direction: all code a report permits
γ(α(l))   all code that "looks the same to the gate" as the current code
l ⊑ …     the real code is one of them — what the gate sees is always coarser than reality
```

**`f(γ(m)) ⊑ γ(f#(m))`** (gate check runs all behavioural checks)

```
m           the report before the change (all ✓)
γ(m)        before the change: the pile of code the gate cannot tell apart (the real code is one of them)
f           the agent's change, applied to code
f(γ(m))     apply this change to every piece in that pile; all possible outcomes
f#          run the gate again after the change
f#(m)       the report after the change
γ(f#(m))    all code the new report permits
⊑           every possible outcome on the left must be inside what the right permits
            — in words: every consequence the change could have must be visible to the new report.
              So the scope of the check must not be smaller than the impact of the change;
              behavioural checks cannot be run partially
```

**`l ⊑ AC(l,u) ∧ u ⋢ AC(l,u)`** (each proposal by the agent)

```
l              what is confirmed as "must be able to" (lower: example specs)
u              the confirmed "must never cross" boundary (upper: constraints + properties)
AC(l,u)        the proposal the agent hands in this round
l ⊑ proposal   the proposal must not lose anything already achieved — hence lower runs in full every time
u ⋢ proposal   the proposal must be genuinely narrower than the boundary, not "promise nothing" — hence escape hatches are banned
∧              only when both hold is progress guaranteed this round
```

**`lfp = fⁿ(⊥)`** (the agent fixes using the counterexample and runs again)

```
⊥           start from nothing
f           one round of change + one round of check
fⁿ(⊥)       the state after n rounds
lfp         the state that no longer changes — VERDICT "mergeable"
```

**`ρ = α∘γ`** (run reduce when done)

```
γ           a function → what it actually does
α           what it actually does → the shortest way of writing it
ρ           replace every function by the shortest way of writing the same thing
            — two functions equal after ρ = they are duplicates
```

**`M₁ =_L M₂ ⟹ P(M₁) =_L P(M₂)`** (hyper observer)

```
M₁, M₂      two worlds: one without a certain module, one with it
=_L         equal on the "trusted part"
P(·)        the observable result after running
⟹          same trusted part ⟹ same result — that module may not secretly influence others
```

## 5. One-page version

```
Starting a project   CLAUDE.md → declaration area → specs skeleton → gate all ✓ → only then code
Each task            human writes spec → agent implements → gate check → route by VERDICT
Never changes        only the human edits the declaration area; escape hatches are always banned; behavioural checks always run in full
```
